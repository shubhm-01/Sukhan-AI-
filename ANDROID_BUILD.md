# Sukhan AI Android APK

The Android build is generated by GitHub Actions using Capacitor. The workflow creates the native Android project in the runner, builds a debug APK, and uploads it as the `sukhan-ai-debug-apk` artifact.

## Start a build

1. Open the repository's **Actions** tab.
2. Select **Android APK**.
3. Select **Run workflow**.
4. Deploy the Express backend from `server.ts` to an HTTPS Node.js host. Configure the server-side `GEMINI_API_KEY` secret on that host. The host must pass its assigned `PORT` environment variable to the server.
5. Verify `https://YOUR_BACKEND_HOST/api/health` returns `ok: true` and `aiConfigured: true`. Do not share the API key itself.
6. Enter the HTTPS origin of the deployed backend in **api_base_url** (for example, `https://api.your-domain.example`). Use only the origin, without a trailing `/api`.
7. Download the `sukhan-ai-debug-apk` artifact from the completed run and unzip it to get `app-debug.apk`.

Alternatively, configure the repository Actions variable `SUKHAN_API_BASE_URL` to the same HTTPS backend origin. Normal APK builds now fail when this URL is missing, rather than producing an APK whose AI calls cannot reach the backend. For a deliberate UI-only smoke test, manually run the workflow with `allow_ui_only=true`.

## Important: backend is separate

The existing Express server in `server.ts` is not bundled inside the Android APK. The APK contains the React web app inside a Capacitor Android shell. AI chat, chat synchronization, Radif suggestions, and server-backed recitation require the Express API to be deployed and reachable over HTTPS.

If no API URL is supplied, the workflow still builds a package for UI smoke testing, but server API calls will not work from the installed APK. Do not treat that build as a production-ready app.

Before public release, secure the server-side chat routes with verified Firebase ID-token authentication and enforce per-user authorization. The client-provided `ownerId` must not be treated as proof of identity. Also verify Firebase Google sign-in on a physical Android device; the current web implementation uses popup-based sign-in and may need native-compatible handling.

This workflow produces an **unsigned debug APK**, suitable for internal testing. A Play Store or shareable production release needs a signed release build and protected signing credentials.
